## 5. Risks

1. **Group-membership scope-bleed risk is server-side and already closed, but the WEB layer must not re-open it via stale query keys.** `WorkspaceAccessDialog`'s groups list must invalidate `queryKeys.groups.all()` (org-scoped) but its OWN binding write invalidates `queryKeys.workspaceAccess.list(workspaceId)` — confirm `use-workspace-access.ts`'s `useSetWorkspaceAccess` (already correct, `hooks/use-workspace-access.ts:26-29`) is what WP-B's new dialog actually calls, not a hand-rolled mutation that forgets the invalidation. This is exactly the "`setQueryData` after org switch" failure mode the task warns about — org-scoped query keys already correctly derive from `scope()` in `lib/api/keys.ts` (org id + workspace id baked into every key), so an org switch naturally invalidates by virtue of the key changing, **provided no new hook this phase hardcodes a key without going through `queryKeys.*`**. Audit every new hook (`use-budgets.ts`, `use-agent-defaults.ts`, new usage client) for this.
2. **Server-right/client-wrong scope bugs — org-scoped-credential endpoints called from a workspace context.** `org/usage`, `org/budgets`, `org/members`, `org/groups`, `org/domains`, `PATCH /org` all 403 a workspace-scoped credential (`org-usage.ts`'s guard, `org-budgets.ts`'s doc comment, `org-members.ts:53-58`, `routes/org.ts:62-68`). The web app authenticates via cookie session (always effectively org-scoped for these admin surfaces since the caller resolves org context server-side), so this should never surface in normal use — but if any new page reuses a workspace-scoped fetch helper (e.g. copies a pattern from `lib/api/agents.ts` that threads `x-workspace-id`) instead of the org-scoped `apiGet` pattern `groups.ts`/`domains.ts`/`org-members.ts` already use, it will 403 silently. **Concretely audit the new `usage.ts`/`budgets.ts`/`agent-defaults.ts` clients** — `agent-defaults.ts` is deliberately WORKSPACE-scoped (`/workspaces/:id/agent-defaults`, `requireWorkspaceManagement`) which is correct and different from the other three; don't accidentally "fix" it to look like the org-scoped ones.
3. **Budgets tab mount point is the one place the task brief's own wording ("port from the fork") conflicts with the already-shipped API contract.** See §4 above — building it under per-workspace `connections/(tabs)/budgets` (as the OLD fork had it) will 404/error against every workspace-scoped secret the create-budget dialog might offer, since `useMeteredSecrets` reads `secrets.listScoped("organization")`. Flag this explicitly in WP-B's PR description so the reviewer doesn't "fix" it back to match the literal fork structure.
4. **`create-door.ts`'s test currently pins the WRONG (upstream) behaviour as correct** (`create-door.test.ts:12-30`) — a dev agent grepping for "expected behaviour" in the existing test suite before reading `plan.md`'s principle 5 will conclude the current `"hosted"`-primary-for-new-users behaviour is intentional and skip the fix. This is the single highest-risk item to silently miss in this phase; call it out explicitly in the WP-B kickoff, not just in this doc.
5. **Stale `loading.tsx`/`metadata.title` on newly-real pages.** Several `ComingSoonCard` stub pages may currently lack a route-level `loading.tsx` (nothing to load) or have a `metadata.title` that doesn't match the new page's actual `<h1>`/`PageHeader title` (e.g., if the stub's title differs subtly from the real page's). Audit every route this phase touches, per WP-C's a11y sweep item.
6. **`ResourceScopeFields`'s `IS_CLOUD` gate is a live bug, not a stand-in** — until WP-C's fix lands, the GitHub picker plan.md says to KEEP is unreachable in this onprem-only fork regardless of how well WP-C builds the picker component itself. If WP-C's PR only adds the component but doesn't also fix `resource-scope.tsx`'s gate, the feature ships dark and nobody notices in code review (it "looks done"). Explicitly test this end-to-end in browser QA (§6), not just via component unit tests that render the picker directly.
7. **Cross-WP shared-file appends to `ee/settings/actions.ts`** (WP-A owns `getOrganizationData`/`deleteOrganizationAction`; WP-C needs to add `createOrganizationAction` to the same file for its create-org page). Low risk (additive exports, textual merge), but sequence WP-A's PR to merge before WP-C's final types/create-org PR, or have WP-C stub its own temporary copy and delete it at merge time if ordering can't be guaranteed.
8. **The `SetWorkspaceAccessInput` type gap** (§3) is the one place this plan asks for a `packages/api` change during a nominally "web-only" phase. If the zod-inferred type truly isn't exported anywhere, WP-C should add one line to `packages/api/src/ee/validations/directory.ts` (`export type SetWorkspaceAccessInput = z.infer<typeof setWorkspaceAccessSchema>;`) rather than leave a hand-duplicated type in `types.ts` — confirm this doesn't fight with any of the three api-worktree branches still open.
