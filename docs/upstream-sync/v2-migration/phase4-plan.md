# Phase 4 (relay stack) implementation plan

Branch `phase4/relay`, stacked on `integration/phase1-2` (upstream v2.6.0 + our Phases 0–2). Four work packages, sized for four parallel developers in separate worktrees. Source material: our own Apache-2.0 code on branch `origin/phase5/cert-token-binding` (PRs #2→#3→#4→#5 stacked; read via `git show origin/phase5/cert-token-binding:<path>`) — there is no licensed upstream `ee` code in this area, so this is a straight port, not a clean-room rewrite. Target: `apps/gateway/` (a Cargo workspace of crates) and `packages/api/` (Hono routes) as they exist on `integration/phase1-2` today. `docs/remote-gateway-deploy.md` is the old operator-facing design and is superseded by this plan's §4/§Risks for anything that changed.

## 0. What v2 already has that changes the design

The old flat gateway (`apps/gateway/src/gateway.rs`, ~2800 lines) and the v2 gateway's `crates/server/src/lib.rs` (~1480 lines) are the same program, restructured into crates — the port is far more direct than a naive reading of "workspace of crates" suggests. Specifically:

1. **`Entrypoint` already exists and is built for exactly this.** `crates/server/src/entrypoint.rs:22-29` defines `trait Entrypoint { fn name(&self) -> &'static str; async fn run(self: Box<Self>) -> Result<()>; }`, and `run_all` (`:41-73`) spawns every entrypoint in a `JoinSet`, aborts the siblings on the first fatal error, and propagates it tagged with `entrypoint = name`. `crates/onecli-gateway/src/main.rs:261-262` already does `let entrypoints: Vec<Box<dyn Entrypoint>> = vec![Box::new(server)]; server::entrypoint::run_all(entrypoints).await`. This is the seam the old code's `tokio::try_join!(plain_loop, mtls_loop)` (`gateway.rs:604-608`) should have been all along — the mTLS listener becomes a **second, independent `Entrypoint`**, not a second branch inside `GatewayServer::run()`.
2. **`handle_connect`/`handle_http_proxy`/`handle_connection` still live beside `GatewayServer`**, in the same crate (`crates/server/src/lib.rs:786-1200`+), unchanged in shape from `gateway.rs`. They currently take no `client_identity`/`on_mtls` parameters (`lib.rs:786-791`, `:840-844`, `:1003-1007`) — v1's threading of those two extra params through all three functions is the one mechanical, low-risk diff this phase reintroduces.
3. **`GatewayServer::new()` no longer returns `Result`** (`lib.rs:225-232`, vs. v1's `pub fn new(...) -> Result<Self>`) and takes 6 params, none of them mTLS/client-CA/binding related. `GatewayState` (`crates/context/src/lib.rs:39-63`) has no `client_ca`/`binding_mode` fields, and `ProxyContext` (`context/src/lib.rs:26-35`) has no `client_identity` field. All three are additive gaps to close, not behavior to reconcile.
4. **The plaintext listener has no `GATEWAY_PLAIN_BIND` today.** `GatewayServer::run()` binds `SocketAddr::from(([0, 0, 0, 0], self.port))` unconditionally (`lib.rs:264`). Porting the mTLS listener without also porting `GATEWAY_PLAIN_BIND` would ship a deployment that cannot ever restrict the plaintext bypass — this phase must port both v1 pieces (the bind-address knob and the "non-loopback plain bind defeats binding enforcement" warning), not just the parts PRs #2–#5 originally added on top of an already-configurable plain bind.
5. **`CertificateAuthority` (`crates/ca/src/lib.rs`) has no `ca_cert_der()`** (only `ca_cert_pem()`, `:122`) — v1's SPKI-collision guard (comparing `GATEWAY_CLIENT_CA` against the MITM CA's own public key) read `ca.ca_cert_der()` directly. Cheapest fix: the new `client-ca` crate parses `ca_cert_pem()`'s output back to DER itself; this avoids touching `crates/ca` at all.
6. **`cache::CacheStore` already has the exact typed helper v1's `resolve_host_tenant` needs**: `impl dyn CacheStore { pub async fn get<T: DeserializeOwned>(...); pub async fn set<T: Serialize>(...) }` (`crates/cache/src/lib.rs:53-67`), on top of the raw `get_raw`/`set_raw`/`del`/`del_by_prefix`/`incr`/`incrby` trait methods. `resolve_host_tenant`'s `state.cache.get::<Option<db::ClientHostRow>>(...)` ports unchanged.
7. **`db` is one flat file** (`crates/db/src/lib.rs`, `pub struct FooRow` + `pub async fn find_foo(...)` pairs, runtime `sqlx::query_as::<_, T>()` — not the compile-time `query_as!` macro, so a new query has no `DATABASE_URL`-at-build-time or migration-ordering compile dependency). `ClientHostRow`/`find_client_host_by_spiffe` is one more pair in that file, verbatim from v1's `db.rs:83-138`.
8. **`proxy::response` (`crates/proxy/src/response.rs`) already has `proxy_auth_required()` and `bad_gateway()`** (used by `handle_connect`/`handle_http_proxy` today) but no `binding_denied()` — one function to add.
9. **The inbound `X-Gateway-Secret` check WP-B needs does not exist anywhere in the gateway.** `grep -rn GATEWAY_INTERNAL_SECRET apps/gateway/crates` finds exactly one hit: `crates/vault/src/onepassword_api.rs:63-66`, and it is the **outbound** direction (gateway → Node, mirroring `packages/api/src/middleware/internal-auth.ts`'s inbound check on the Node side). Node → gateway, checked _by_ the gateway, is new code in both directions of the v1 port: v1 wrote it once (`gateway.rs:799-836`); this phase writes the gateway-side inbound check for the first time in v2, alongside the Node-side outbound caller.
10. **Workspaces, not Projects.** `ApiKey` (`packages/db/prisma/schema.prisma:378-413`) has `scope: "workspace" | "organization"`, `workspaceId`/`organizationId` both nullable, `key` prefixed `oc_`/`oc_org_`. `client_hosts` (per `plan.md`) is keyed by `workspace_id`. `connect::resolve`'s `ConnectResponse` (and therefore `binding::evaluate`'s `token_project`/`token_org` params) is already renamed `workspace_id`/`organization_id` throughout `crates/proxy/src/connect.rs` and `crates/server/src/lib.rs:909-916`.
11. **The Node-side route pattern is `auth({ requireWorkspace, role })`** (`packages/api/src/middleware/auth.ts:47-90`), not the old `authMiddleware`/`requireProjectId` pair. `requireWorkspace` defaults to `true` and already resolves an org-scoped key's workspace from an explicit `X-Workspace-Id` header (validating org membership before trusting it, `auth.ts:56-66`) — this is the existing, already-shipped mechanism for "an org-scoped key acting on one workspace it can see," and answers this phase's "how does an `oc_org_` key enroll a relay" question with no new code: use `auth({ requireWorkspace: true })` (the default) on the new route, exactly like every other workspace-scoped write in this codebase.
12. **`AUDIT_ACTIONS.MINT` and the `ssh-service.ts` precedent already exist** (`packages/api/src/services/audit-service.ts:35-38`, "a short-lived \[...\] certificate \[...\] — an access GRANT, so first-class rather than CREATE") for exactly this shape of event. There is no `AUDIT_SERVICES.CLIENT_HOST` yet — one line to add, following the `SSH: "ssh"` entry's doc-comment style.
13. **Rate limiting is a permanent no-op** in this fork (`packages/api/src/ee/middleware/rate-limit.ts:14-25`: Redis was dropped, and "off" was the documented Redis-less degraded mode, made permanent). V1's `POST /v1/gateway/client-cert` PR left "rate-limit this route" as an explicit follow-up; that follow-up is still not implementable today without inventing new in-memory limiter infra, so it stays a follow-up here too (§ Open questions).
14. **`apps/gateway-e2e` spawns one binary and greps its stdout for readiness lines.** `startGateway` (`apps/gateway-e2e/src/gateway.ts:246-320`) waits for the literal line `"listening for connections"` before returning a handle. A second entrypoint MUST log a **different** line (`"listening for mTLS connections"`, matching v1) so the existing helper is never confused about which port is up — and a new e2e helper is needed for tests that specifically need the mTLS port ready, since `run_all` starts both entrypoints concurrently and nothing today guarantees ordering between them. `gatewayBinary()` (`apps/gateway-e2e/src/binary.ts`) resolves one binary path usable for both `onecli-gateway --port ...` and `onecli-gateway relay ...` — no second binary needed for e2e.

## 1. Work packages

Recommended split matches `plan.md`'s named crates (`client-ca`, `relay`, `binding`) plus one crate-free "wire it together" package. Owned files below are new; "Free files" are exact edits to files another WP (or nothing) already owns — kept to the minimum the port structurally requires.

Ports v1's `client_ca.rs` + `client_ca_authority.rs` (PRs #2 + #3's gateway half) plus the `GATEWAY_PLAIN_BIND` piece of `gateway.rs` that v2 never got.

- `crates/context/src/lib.rs`: `GatewayState` gains `pub client_ca: Option<Arc<client_ca::ClientCa>>`. (`ProxyContext.client_identity` is **not** added by this phase — v1 marked it `#[allow(dead_code)]` and never read it; binding enforcement threads identity as a plain function parameter, resolved _before_ `ProxyContext` is built, exactly as v1 did. Add it only if a future phase needs it.)

- `crates/onecli-gateway/src/main.rs`: load/generate the client-CA authority (v1 `main.rs:278-302`: skip generation and leave `client_ca: None` when `GATEWAY_CLIENT_CA` is operator-set, matching the "externally managed trust anchor" posture), call `client_ca::MtlsConfig::from_env(ca.ca_cert_der() [see below], cli.port, fallback_client_ca_pem)`, pass `client_ca` into `GatewayServer::new(...)`, and — when `mtls` is `Some` — push `Box::new(server::mtls::MtlsEntrypoint::new(server.state().clone(), mtls_config))` onto the `entrypoints` vec alongside `Box::new(server)`.

Note on `ca.ca_cert_der()`: since `crates/ca` has no such accessor (§0.5), `main.rs` instead passes `ca.ca_cert_pem()` (a `String`) to `MtlsConfig::from_env`, and `client-ca`'s SPKI guard parses that PEM to DER internally (one extra `pem_to_der_certs` call versus v1, which had DER already in hand) — net zero behavior change, one less crate touched.

Behavior spec: identical to v1's `client_ca.rs`/`client_ca_authority.rs` — see the file-by-file summary above and the SECURITY comments quoted in this plan's research (fail-closed on any load/parse error, `WebPkiClientVerifier` with no `allow_unauthenticated`, HTTP/1.1-only ALPN, SPKI (not whole-cert) comparison for the MITM-CA collision guard, `sign_csr` never reads the CSR's own subject/SAN/EKU/validity — every identity field is server-supplied).

Tests: port v1's ~70 unit tests (identity extraction/sanitization table, PEM/DER helpers, SPKI-collision guard, `MtlsConfig::from_parts` fail-closed matrix, `sign_csr` identity-override negative test via parsing the issued X.509, tampered/garbage/oversized/Ed25519 CSR rejection). New e2e `apps/gateway-e2e/tests/mtls.test.ts`: no cert / wrong CA / expired cert → rejected (assert the specific rustls alert, matching v1's matrix); valid cert → accepted, `/healthz` returns 200 (no enforcement in this WP); `GATEWAY_PLAIN_BIND=127.0.0.1` actually refuses a connection on the external interface (or, in the sandboxed e2e environment, assert the bound address in the boot log); boot logs both `"listening for connections"` and `"listening for mTLS connections"` and the harness's existing readiness wait is unaffected.

### WP-C: `relay` subcommand (M, 3–4 days)

Ports PR #4. Depends on WP-A's `client-ca` crate for `pem_from_value`/`load_client_ca_roots` (a 2-function surface, frozen by this plan — WP-C can stub these two signatures and start day 1, then drop the stub once WP-A merges).

Free files:

- `crates/onecli-gateway/src/main.rs`: `Cli.command: Option<Command>` (`#[command(subcommand)]`), `enum Command { Relay(relay::RelayArgs) }`, dispatched as the very first thing after `shutdown::install()` and before any CA/DB/crypto/vault bootstrapping (v1 `main.rs:231-246` verbatim pattern) — relay mode shares only the rustls provider install and signal handling with server mode.
- `crates/onecli-gateway/Cargo.toml`: path dep on `relay`.
- `apps/gateway/Cargo.toml`: add `"crates/relay"` to `members`; add `arc-swap = "..."` to `[workspace.dependencies]`.

Behavior spec: a blind byte-splice, never parsing the agent's CONNECT line or headers. Enrolls once at startup (fail-closed: an unreachable/failing enrollment aborts `run()` before any listener binds), renews at `not_after - max(lifetime/3, 5min)`, backs off exponentially (5s → 300s cap) on a renewal failure without hot-looping on a TLS-rebuild failure specifically, and stops renewing (rather than retry forever behind an expired cert) once the current certificate has actually expired. Every tunnel failure — expired cert, dial failure, TLS handshake failure/rejection, dial timeout — funnels through one `refuse()` → drain-then-`502`-then-close; there is no plaintext or direct-egress fallback anywhere in this crate.

Tests: port v1's ~90 tests (host_part, persist/load round trip, 0600 atomicity + hard-error-on-create-failure, `next_renewal`'s three lifetime bands + past-due, `renewal_loop`'s backoff-after-rebuild-failure regression test, `enroll`'s bearer-auth/camelCase-parsing/host-id-on-renewal/non-2xx/unreachable cases, `splice`'s byte-preservation/timeout/expired-cert/untrusted-server-cert cases). New e2e `apps/gateway-e2e/tests/relay.test.ts` — see §4.

## 3. Risks

1. **Two WPs edit `GatewayState`/`context/src/lib.rs` and `server/src/lib.rs`'s `build_router`/`run()` in the same phase.** Following the `phase2-plan.md` precedent (multiple WPs appending to `ee/index.ts`), this is a pure-append merge if each WP adds one field/one route line and nothing else on those lines — call this out explicitly in each PR description so the merge order (WP-A → WP-B/WP-D, order between B and D doesn't matter) is a fast-forward, not a real conflict.
2. **`run_all`'s "abort the siblings on first fatal error" semantics change the failure mode of a plaintext-only deployment.** Today a plaintext bind failure is the only way to fail; once a second entrypoint exists, an mTLS bind failure (e.g. a bad `GATEWAY_TLS_CERT`) now also takes down the plaintext listener via `set.abort_all()` (`entrypoint.rs:59-63`). This is the _fail-closed_ behavior v1 already had via `tokio::try_join!` (a bind failure on either port aborted startup before either accept loop ran) — confirm this is still true once mTLS is validated (`MtlsConfig::from_env`) **before** either entrypoint starts running, not just before its own accept loop, so a bad mTLS config fails at startup rather than tearing down an already-serving plaintext listener mid-flight.
3. **The e2e readiness-detection collision (§0.14) is a real, not hypothetical, risk** — `apps/gateway-e2e`'s `startGateway` and every scenario built on it assume exactly one `"listening for connections"` line. Get the mTLS entrypoint's boot log text reviewed for uniqueness before writing tests against it, and add a `waitForMtlsListening`-shaped helper rather than reusing `scenario.ts`'s existing readiness wait for tests that need the mTLS port specifically.
4. **`ProxyContext.client_identity` is deliberately deferred** (§WP-A) — if a later change (e.g. audit logging inside `mitm.rs`/`forward.rs`) needs it, adding the field is a one-line, additive `context/src/lib.rs` change; don't add it speculatively now since nothing in this phase reads it.
5. **The `client_hosts` FK's `ON DELETE` behavior is unverified against this fork's actual workspace-deletion code path** (§WP-B) — v1's `RESTRICT` assumed a project could not be deleted with dependents; this fork's `Workspace` deletion semantics may already cascade related tables. Get this confirmed with a pg test before merging the migration, not assumed from the old schema.
6. **`x509-parser` and `arc-swap` are net-new workspace dependencies.** Check `cargo tree` for an existing transitive pin of `x509-parser` (rcgen's own dependency tree may already resolve one) before choosing a version, so `Cargo.lock` doesn't end up with two incompatible versions of the same crate.
7. **The internal `X-Gateway-Secret` check is new code on the gateway side, not a port of existing code** (§0.9) — it is easy to accidentally reuse or alias `vault::onepassword_api::internal_secret()` (same env var, opposite direction, different `OnceLock`); keep them as two separate functions the way v1 did, with the doc comment cross-referencing the other direction.
8. **Binding enforcement is only as strong as the plaintext listener's bind address** (v1's own risk, restated because it is now split across two WPs): WP-A ports the base `GATEWAY_PLAIN_BIND` mechanism, WP-D adds the binding-mode-aware warning on top of it. If WP-A's port is incomplete (e.g. the knob exists but the warning text is dropped), WP-D's warning has nothing to extend. Sequence WP-D's warning addition strictly after WP-A merges and review both warnings together.
9. **Relay's `RELAY_GATEWAY_SERVER_CA` vs. the client CA's `caPem` confusion is the single highest-value thing to get right in code review** (v1 flagged it with a SECURITY comment for exactly this reason) — a reviewer should specifically check that `renew.rs`/`tunnel.rs` never read `EnrollResponse.ca_pem` for anything other than passthrough/display.

## Orchestrator vetting notes (2026-09-15)

Accepted as written, with these decisions:

1. **`client_hosts.workspace_id` is `ON DELETE CASCADE`**, `organization_id` is `ON DELETE SET NULL`. Nothing in the product can list or delete client hosts yet, so a `RESTRICT` would make a workspace undeletable with no remedy; a cascaded host simply stops resolving and binding denies it (no row → deny), which is the fail-closed direction. WP-B adds a pg proof: deleting a workspace removes its `client_hosts` rows and the api-server's workspace-delete path needs no change.
2. **`binding_denied()` follows the existing gateway error shape**: `{"error": "identity_not_permitted", "message": "<human sentence>"}`, modelled on `access_restricted` in `crates/proxy/src/response.rs`. `host_revoked` and the workspace/org mismatch use the same `error` value with a different `message`; the reason string goes to the log line, never to the client.
3. **Rate-limiting the enroll route stays a follow-up.** Enrolment needs a valid workspace-scoped credential already; a token bucket without Redis is new infrastructure this phase does not build.
4. **`mintClientCert` targets the existing internal-URL export** in `packages/api/src/lib/env.ts` (the one computed at line 29 from `GATEWAY_INTERNAL_URL` with the `gatewayHttpOrigin()` fallback). No new env var.
5. **`docs/remote-gateway-deploy.md`**: the full rewrite is Phase 5's (deployment). WP-C replaces the stale header only: image `ghcr.io/whybutter/onecli-gateway`, relay `--api-url` is the **api-server origin** (not the web app), and a pointer that Phase 5 owns the deployment guide.
