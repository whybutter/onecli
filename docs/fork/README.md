# OneCLI fork reference

This is the index of everything this fork adds or changes on top of upstream OneCLI. It exists so
a maintainer who knows OneCLI, but has not read the migration plans, can scan two minutes of tables
and then drill into exactly the code, config, tests and history for any change.

This fork is an independent, Apache-2.0-licensed fork of OneCLI v2, rebased onto upstream v2.6.0.
The three directories upstream ships as enterprise-licensed code — `apps/gateway/crates/ee/ee/`,
`packages/api/src/ee/`, `apps/web/src/ee/` — are clean-room rewrites owned entirely by this fork,
at the same paths and export names so the free code around them needed no changes. There is no
license flag anywhere in the tree: `entitled()` (gateway,
[`apps/gateway/crates/common/src/edition.rs`](../../apps/gateway/crates/common/src/edition.rs)) and
`isEntitled()` (API, [`packages/api/src/lib/entitlements.ts`](../../packages/api/src/lib/entitlements.ts))
both always return `true`, so every feature upstream gates behind a license is simply on, always.
`EDITION`/`NEXT_PUBLIC_EDITION` (`cloud` vs `onprem`) is a separate, still-live axis — entitlement
and edition are independent.

Nanoclaw is this fork's agent runtime: BYO agents are the primary create-agent door in the
dashboard regardless of whether upstream's hosted-agent runner is registered, and that runner stays
in the tree, off by default, out of this fork's publish matrix. There is no Redis and no
multi-instance story — a single gateway process is the deployment model, reachable either directly
(same host) or through this fork's own remote relay stack (mTLS + short-lived client certificates)
for a gateway and its agents that live on different machines.

## Status / roadmap

**Done:** Phases 0–4 and 5a — foundation/entitlement (0), gateway RBAC/budgets/conditions (1), API
control plane (2), web dashboard surfaces (3), remote-gateway relay stack (4), invite-only
registration (5a).

**Next:** Phase 5b (nanoclaw + Dokploy deployment, needs the operator) and Phase 6 (cutover to a
fresh production database on `main`).

**Deferred, recorded as explicit decisions, not gaps:** webhooks (#7, "next version" after
cutover), app availability (gateway keeps only the pure block function), role mappings (no API or
UI surface), a Dropbox folder browser (GitHub-only picker), OpenAI metering (Anthropic-only budget
enforcement today), Vanta (#1, parked).

**Operator env vars for the remote gateway** (`GATEWAY_MTLS_PORT`, `GATEWAY_TLS_CERT`/`_KEY`,
`GATEWAY_CLIENT_CA*`, `GATEWAY_BINDING_ENFORCEMENT`, `GATEWAY_PLAIN_BIND`, `GATEWAY_INTERNAL_URL`,
`RELAY_*`) are documented with defaults in [`remote-gateway-relay.md`](remote-gateway-relay.md) and
as a commented block at the end of [`.env.example`](../../.env.example).

## How to keep this current

Any PR that touches fork-owned behaviour, a free (non-`ee/`) file, an env var, or a migration
updates the relevant `docs/fork/` page and [`upstream-divergences.md`](upstream-divergences.md) in
the same PR. A plan for that work states which `docs/fork/` pages it will touch; a review checks
that they were actually updated before approving. See the "Fork documentation" section in the root
[`CLAUDE.md`](../../CLAUDE.md) for the exact rule.
