# OneCLI v2.6.0 `packages/api/src/ee` — behavioural specification

Source of truth: upstream `onecli/onecli` at v2.6.0, `packages/api/src/ee/**`, read together with the free seams it plugs into (`providers/`, `edition-defaults.ts`, `middleware/auth.ts`, `services/workspace-access-check.ts`, `services/organization-service.ts`, `services/invitation-service.ts`, `routes/workspaces.ts`) and the tests in `ee/**` and `licensing/**`. This document describes WHAT the code does so a clean-room implementation can reproduce the behaviour without reading it. No code is reproduced.

Conventions used below

- "org" = organization; "ws" = workspace; "member" = an `organization_members` row.
- HTTP paths are given relative to the API root; the shared app mounts everything under `/v1` (so `/org/members` is really `/v1/org/members`). The SCIM app is a separate Hono app mounted at `/scim/v2` on the api-server root.
- "admin auth" = `auth({ requireWorkspace: false, role: "admin" })`; "read auth" = `auth({ requireWorkspace: false })`.
- `ServiceError(CODE, message)` is the domain error class; the shared error handler maps it to `{ error: { message, type } }` with the status/type table in Appendix B. Route-local zod failures instead return a plain `{ error: "<first issue message>" }` with status 400 (or 422 where noted). Both shapes exist on the wire today.
- "audited" means a `withAudit` wrapper, which writes one `audit_logs` row (status `success`, `source` defaults to `app`) and then flushes the gateway cache for the given `workspaceId` and/or `organizationId`. `recordAuditEvent` writes the row but does NOT flush the cache.

### 0.2 Roles, hierarchy, suspension

- `OrgRole` = `owner` | `admin` | `member`, ranked 3/2/1. `hasMinimumRole(role, min)` is `role != null && rank(role) >= rank(min)`.
- `ASSIGNABLE_MEMBER_ROLES` = {`admin`, `member`}. `owner` is conferred only by creating the org; it is never assigned, transferred, demoted, removed or suspended. There is exactly one owner per org by construction and no ownership-transfer feature exists.
- `getUserRole(userId, orgId)` returns the membership role, or `null` when there is no membership **or the membership status is `suspended`**. This one function is the suspension choke point: every role gate, org-key re-check, workspace-key re-check and the access checker deny through it.
- `requireRole(userId, orgId, min)`: when `CAPS.rbac` is off it returns `role ?? min` (flat team, everyone passes). Otherwise: no role → `FORBIDDEN "Not a member of this organization"`; below threshold → `FORBIDDEN "Insufficient permissions"`; else returns the role.
- `canManageAllWorkspaces(role)` = `!CAPS.rbac || rank(role) >= admin`.
- Placeholder identities: emails ending `@onecli.internal` (provision seat-warmers) are hidden from every human list; `externalAuthId` prefixes `provision-`, `scim-`, `local-` mark non-Cognito identities.

### 0.3 The shared auth middleware's role option (free code, consulted by every EE route)

`auth({ role: "admin" })`: after API-key or session auth, if `CAPS.rbac`: needs the role resolver (missing → 403 "Not a member of this organization"), resolves the caller's role via `getUserRole`; null → 403 "Not a member of this organization"; below → 403 "Insufficient permissions" (both `type: "authentication_error"`); the resolved role is stored on the auth context. If `CAPS.rbac` is off: only an active-membership fence (suspended/departed → 403 "Not a member"). Separately, an **org-scoped API key** whose holder is no longer admin fails at key authentication itself and answers **401** (strict `oc_` bearer mode) — the route tests call this "the demotion re-check".

### 0.4 Directory pagination envelope (§3.5)

Every directory-scale list (members, groups, group members, user→groups) returns `{ data: T[], nextCursor: string | null }`. `limit` defaults to 50, clamped to 1..200 (the query schema rejects >200 with 400). The cursor is base64url of a JSON object of string values encoding the keyset position of the last row; a malformed/truncated cursor or one with non-string values → `ServiceError("BAD_REQUEST", "Invalid cursor")`. Pages are read with `limit + 1` rows; `nextCursor` is set only when the sentinel row exists. Common query schema: `limit` (coerced int 1..200), `cursor` (non-empty string), `q` (trimmed, 1..200 chars).

## 1. Team / members

### 1.1 Purpose

Manage the human members of an organization: list them, change roles, suspend/reinstate, remove, let a member leave, mark break-glass SSO exemptions, and (licensed) provision members by email. Role writes stay consistent with directory group→role mappings and with the gateway's authorization cache.

On a self-host the outcome is always `"skipped"`; keep the field for wire compatibility.

### 1.4 Invariants and business rules

- Owner protection is a domain rule, alive without a license: the owner cannot be removed, suspended, demoted, or leave (web `leaveTeam` refuses with "An organization requires at least 1 owner"). There is no last-admin protection — an admin may demote themself.
- Cross-org fencing: every read/write is keyed by `(organizationId, userId)`; a user id from another org reads as "not a member" → 404 (routes) / plain Error (service).
- Idempotency: suspend on suspended → 409; reinstate on active → 409 (human API). The SCIM/directory twins are idempotent instead (§8.6).
- Suspension outranks mappings; owners are never IdP-managed even inside a mapped group.
- Placeholder members and suspended members still occupy a seat for quota purposes (cloud only).
- The web server actions add their own guards: `removeTeamMember` refuses self ("You cannot remove yourself from the organization") and requires admin; `leaveTeam` refuses owners; `getWorkspacesDeletedOnRemove` is admin-gated. Their audits use action `delete`/`update` with a non-constant service string `"team"` and metadata `{ removedUserId }`, `{ leftOrganization: true }`, `{ targetUserId, newRole }` — the fork should normalize these onto `MEMBER`.

### 1.5 Side effects

- Tables: `organization_members` (role/status/suspendedAt/ssoExempt), `api_keys` (deletes), `workspace_access` (deletes), `group_members` (deletes), `workspaces` + all workspace children (cascade via `deleteWorkspace`), `users` (`deactivatedAt` on cloud revoke), `audit_logs`.
- Audit rows: see Appendix A rows for MEMBER and API_KEY.
- Gateway cache: `withAudit` on the routes flushes the org; `reconcileMemberRoles` flushes the org itself when it changed something; `deleteWorkspace` flushes the deleted workspace's keys.
- Emails/notifications: none.

### 1.6 Seams

- `initRoleResolver({ getUserRole })` — injected on cloud and on an entitled self-host; the auth middleware, invitations router and policy-reflect redaction read it. Must return the ACTIVE membership role or null.
- `TeamHooks` (`initTeamHooks`): `beforeInviteMember(orgId)` runs in `createInvitation` for every NEW seat (a resend of a still-pending, unexpired invitation skips it) — EE sweeps expired provisions (non-fatal) then asserts the seat cap (no-op without billing); `afterMemberJoined(orgId, userId)` runs after `acceptInvitation`'s transaction — EE reconciles the joiner's role against mappings (IdP wins over the invited role). Both are wrapped so tests can partially mock.
- Invitation routes (free) apply the admin requirement only where a role resolver exists; otherwise any member may invite (flat team).

### 1.7 Edge cases the tests pin

- Suspend: status flipped BEFORE revocation, revocation receives the pre-flip membership count; all four guards leave zero writes.
- Reinstate re-resolves the mapped role after the status flip (a mapping to `member` demotes a reinstated admin).
- Remove: computes ownership inputs pre-delete, revokes after delete; `revokeIdentity:false` → `"skipped"` and no provider call; strips the leaver's shared-in bindings and group memberships scoped to the org; deletes only truly-personal workspaces (workspace filter: created by leaver, `some` binding by leaver, `none` other-user or group binding); deletes nothing when all workspaces are shared or admin-adopted.
- Reconcile: promotes, demotes, never changes an owner, skips suspended, leaves unmatched untouched, no-op when equal.
- changeMemberRole: refuses mapped members with the IdP message; allows unmapped; owner guard precedes the lock; unlicensed → license refusal.
- Routes: PATCH rejects both-at-once/unknown/empty; owner suspension maps to 400 with no audit; POST normalizes email case; existing member → 409 no audit; DELETE unknown → 404 typed, owner → 400 before removal.

### 1.8 Fork relevance

**KEEP** (trim the Cognito arm to a constant `"skipped"`; keep `revocation` in responses/audits). Suspend/reinstate, role change with the mapping lock, remove/leave with personal-workspace cleanup, the directory list and the provisioning POST are all self-host-relevant for a small team with real RBAC. Drop `ssoExempt` only if SSO is dropped (see §8).

## 2. Authorization (roles, workspace access, management guard)

### 2.1 Purpose

One place decides who may see, use and manage a workspace and who is an org admin. Usage is bindings-only (a `workspace_access` row, direct or via a group) or org-admin; management is an owner-role user binding or org-admin.

Replace semantics: dedupe users by id (last role wins) and group ids; diff against current rows; users/groups absent from the payload are removed (the creator's own binding included — the "last binding" guard is a UI warning only; org admins remain the backstop); preserved users whose role differs are re-roled in place (never deleted and re-created); additions are validated (new users must be ACTIVE members of the org; new groups must belong to the org) and only additions trip the entitlement gates (preserving or removing a legacy group binding never re-trips a gate; a role change needs no entitlement); no-op when nothing differs (no transaction, `{0,0,0}`); all writes in one transaction; creates use skip-duplicates so a concurrent double-add is idempotent; new rows record `createdByUserId` = actor. Group bindings carry no role (always `member`).

### 2.4 Management guard `requireWorkspaceManagement(authCtx, targetId)`

1. If the caller authenticated with a **workspace-scoped key** and `authCtx.workspaceId !== targetId` → `NOT_FOUND "Workspace not found"` before any DB read (a leaked key cannot manage sibling workspaces). Org keys and sessions are never confined.
2. `canManageWorkspace` → allow (access is not consulted).
3. Else `canAccessWorkspace` → `FORBIDDEN "You don't have permission to manage this workspace"` (a shared-in member).
4. Else `NOT_FOUND "Workspace not found"` (no existence leak).

Used by: PATCH/DELETE `/workspaces/:id` (free routes) and both `/access` routes.

### 2.5 Free code that consults these

- `services/workspace-access-check.ts` (free): `canAccessWorkspaceAsUser` and `userIsOrgAdmin` return true when `!CAPS.rbac`; under RBAC they delegate to the injected checker and, if none is injected, log an error and DENY (a wiring bug must be loud, not a silent open door).
- Callers: session/api-key auth resolution (a key or session naming a workspace the user cannot access is rejected), cron/watch firing, SSH grants, channel ingestion, the web workspace layout (`canAccessWorkspaceAsUser`), the web admin layout (`userIsOrgAdmin`).

### 4.4 Resolution law

- A user's mapped roles = the role mappings of every group (in this org) they belong to.
- Winner = highest `priority`; on a tie `admin` beats `member` (equal-priority pairs can never silently demote); any non-`admin` stored value normalizes to `member`.
- No mapped group → null → "unmatched": the applier leaves the current role untouched.
- Mappable roles are only `admin` | `member`; owners are never IdP-managed.
- `isRoleManagedByIdp(org, user)` = exists ≥1 role mapping whose group has the user as a member. This locks manual role edits (§1.3) and marks `roleManagedByIdp` in `listMembers`.
- Triggers of reconciliation: group membership add/remove/set, group delete, mapping create/update/delete/reorder, invitation accept (`afterMemberJoined`), SSO login (existing and JIT members), reinstate.

## 5. Granular access (session policies / resource scoping)

### 5.1 Purpose

Let a grant (agent ⇄ connection) restrict WHICH resources the injected credential may reach — GitHub App repositories or Dropbox folders — validated at write time against the provider and against the org's boundary; the gateway enforces it at runtime.

### 5.2 Shapes and validation

| Provider           | Policy shape                 | Write-time validation                                                                                                                                                                                                                                                    |
| ------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `github-app`       | `{ repositories: string[] }` | If absent/empty → accepted. Otherwise every entry must appear in the connection's `metadata.repos` list; else BAD_REQUEST `Repositories not available on this installation: <a, b>`.                                                                                     |
| `dropbox`          | `{ folders: string[] }`      | `folders` absent → accepted; not an array → BAD_REQUEST `folders must be an array`; empty → accepted; >100 → BAD_REQUEST `Too many folders selected (max 100)`; each must be a string starting with `/` and ≤1024 chars else BAD_REQUEST `Invalid folder path: <value>`. |
| any other provider | anything                     | Accepted as-is (no granular config).                                                                                                                                                                                                                                     |

Wire schema (free `validations/policy.ts`): the session policy is a strict union of `{ repositories: string[1..1000 items, each 1..400 chars] }` or `{ folders: string[1..100, each 1..1024] }` — the wire REJECTS an empty list. Grants take `resources` tri-state: absent = preserve the existing stack's conditions; `null` = clear; object = set. Direct service callers normalize an empty list to null ("unrestricted"), and list values are sorted for byte-stable storage. An explicit SET runs the edition's policy validator then the org-boundary check; clearing/preserving never runs a validator (removing a restriction must not need an entitlement).

Org boundary (free grants-service): if the org's published rules define a resource boundary for this (agent, principals, connection), entries outside it → UNPROCESSABLE `Outside the access your organization allows for this connection: <entries>`.

Storage: the normalized object becomes the `conditions` of the grant's compiled policy rules; `AgentGrantConnection.resources` is read back from the stack's conditions (object = session policy; arrays are behavioural conditions and never leak into `resources`).

### 5.3 Policy validator seam

- Interface: `validate(orgId, provider, connectionMetadata, policy)` and optional `validateTargets(targets)` (absent = permissive; NEITHER edition implements it).
- Cloud default: `assertCanUseGranularAccess(org)` (entitlement + plan ≥ team) then the shape validation.
- Onprem default (free): `assertEntitled("granular_access")` then the SAME shape validation (loaded lazily). Parity test: same input yields the same verdict through both.
- Called from grants `setConnectionGrant` (explicit resources) and from policy-rule create/update (never publish).

### 5.4 Dropbox folder browser — GET `/apps/dropbox/folders` (router gate `requireEnterprise("granular_access")`; read auth)

| Query                                                                      | Behaviour                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `connectionId` (required), `path` (default `""`; `"/"` is treated as root) | Finds a `dropbox` connection with status `connected` owned by the caller's org (org-scoped or in one of its workspaces); missing/no credentials → 404 `Connection not found`. Subject must exist (NOT_FOUND `Secret not found.`) and be a metered type — only `anthropic` (else BAD_REQUEST `Budgets aren't supported for <type> secrets yet.`).
- Period key must match the gateway: `m:YYYY-MM` (UTC) for monthly, `total` for lifetime; spend is stored in nano-dollars in `budget_spends` keyed `(secretId, organizationId, period)`; the API converts to whole cents with integer math. Spend may lag live Redis by ~5s.
- No authorization beyond entitlement (callers must add "who may budget this secret"), and the gateway binder's eligibility must be widened in the same change.
- `deleteOrganizationContent` clears `budgets`/`budget_spends` as orphan cleanup.
- Fork relevance: **DROP** (keep the two tables' cleanup lines in org delete if the schema keeps them).

## 7. App availability

### 7.1 Purpose

An org-level allowlist deciding which apps a workspace may CONNECT (a provisioning gate; policy rules govern use). "open" = every app for everyone (default); "restricted" = an app is available to a workspace only when a rule granting it names one of the workspace's inherited people.

### 7.2 HTTP contract — `/org/app-availability` (router gate `requireEnterprise("app_availability")`; admin auth on the router)

| Method & path | Request                                                                                                                                       | Success                                                                                                                                                                                                                                                                                                         | Errors                                                                                                                                                                                                                                        |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET           | —                                                                                                                                             | 200 `{ mode: "open"\|"restricted", rules: [{ id, name, userIds, groupIds, providers }] }` oldest first; a missing org reads as open with no rules.                                                                                                                                                              | —                                                                                                                                                                                                                                             |
| PUT           | `{ mode: "open"\|"restricted", rules: [{ id?, name? (≤200, nullable), userIds (≤1000), groupIds (≤1000), providers (≤200) }] (≤1000 rules) }` | 200 the re-read config. Plan gate `assertFeatureAllowed(org,"groups")` runs ONLY when `mode === "restricted"` or `rules.length > 0` — resetting to plain open with no rules is always allowed (a downgraded org can never be locked into a restriction). Audited UPDATE/APP_AVAILABILITY `{ mode, ruleCount }`. | **422** (ServiceError UNPROCESSABLE) on invalid body (bad mode, non-array identities); 403 gate; 400 `Unknown app provider: <id>`; 422 `A referenced identity does not belong to this organization.`; 400 `Duplicate rule id in the request.` |

### 7.3 Write semantics

- Normalize: trim name (blank → null); dedupe users, groups, providers per rule; DROP no-op rules (no identities OR no providers) — they are never persisted, and an existing rule edited down to a no-op is deleted.
- Validate across all rules: every provider is a known app; every user is an ACTIVE org member; every group belongs to the org (exact-count check against deduped id sets — a foreign id fails as a whole).
- Diff by id: ids that belong to THIS org's existing rules are updated (name, providers; identity rows fully replaced); ids not belonging to the org are treated as brand-new creates (never touch another org's row); existing rules absent from the payload are deleted (org-fenced); the mode is always written; one transaction; new rules carry `createdByUserId` = actor.

### 7.4 Derivation (`deriveAvailableProviders(wsId, orgId)`) — the TS mirror of the gateway

- Org not restricted → `null` (= all apps; no further queries).
- Direct users = the workspace's user bindings; direct groups = its group bindings filtered to org groups; candidate users = direct users ∪ members of direct groups; users = candidates that are ACTIVE members of the org; groups = direct groups ∪ every org group those users belong to. No users and no groups → `[]`.
- Result = union of `providers` of every org rule naming any of those users or groups (deduped).
- Exposed through the `AppAvailabilityProvider` seam (cloud default only); OSS never registers it so the connect picker is unfiltered.

### 7.5 Edge cases the tests pin

- Unknown provider 400 before any write; foreign user 422 with an org-fenced, suspended-excluded count; foreign group 422.
- Kept rule updated + identities replaced; new rule created with provenance; mode always written; dropped rule deleted; rule edited to no-op deleted; duplicate id 400; forged id → create (and the org's real absent rule is deleted); no-op rules dropped; ids deduped within a rule.
- Derive: open → null without touching bindings; restricted with no people → []; unions matching rules and org-fences every arm.
- Routes: admin reads; org key below admin → 401; non-enterprise restricting write → 403; open reset allowed on lapsed plan; 422 shapes; valid write echoes.

### 7.6 Fork relevance

**TRIM/KEEP-LATE**: useful only once groups and workspace bindings exist and the gateway enforces it; keep behind the `app_availability` entitlement or drop until needed.

## 8. Identity: domains (full), SSO / SCIM / provisioning (brief)

### 8.1 Org domains — full contract (`/org/domains`; router gate `requireEnterprise("sso")`; admin auth)

| Method & path                        | Request                                                                           | Success                                                                                                                                                                 | Errors                                                                                                                                                                                                                                                                       |
| ------------------------------------ | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/org/domains`                   | —                                                                                 | 200 `[{ id, domain, verificationToken, verifiedAt, createdAt }]` ordered createdAt asc. Never plan-gated (locked page renders).                                         | —                                                                                                                                                                                                                                                                            |
| POST `/org/domains`                  | `{ domain }` (trim, 3..253 chars; shape-only) + `assertFeatureAllowed(org,"sso")` | 201 the row (token included). Audited CREATE/DOMAIN `{ domainId, domain }`.                                                                                             | 400 `Enter a valid domain like example.com` (normalization failure); 400 `Public email providers can't be claimed. Use your company's domain.`; 409 `This domain is already claimed by an organization.` (domain is GLOBALLY unique across orgs, verified or not); 403 gate. |
| POST `/org/domains/:domainId/verify` | — + `assertFeatureAllowed(org,"sso")`                                             | 200 the row with `verifiedAt` set. Audited VERIFY/DOMAIN `{ domainId, domain, verified: true }` (also on the idempotent already-verified path).                         | 404 `Domain not found` (cross-org = 404); 400 `TXT record not found yet. DNS changes can take a few minutes to propagate.`; 403 gate.                                                                                                                                        |
| DELETE `/org/domains/:domainId`      | —                                                                                 | 204; audited DELETE/DOMAIN `{ domainId }`. DELIBERATELY never plan-gated (teardown must survive a plan lapse because a verified domain keeps steering logins into SSO). | 404 when nothing matched (wrong org or id).                                                                                                                                                                                                                                  |

Normalization: trim, lowercase, IDNA/punycode to ASCII, strip one trailing dot; must match `^([a-z0-9-]+\.)+[a-z0-9-]{2,}$` (labels + a 2+ char TLD; `nodot` and `not a domain` fail). Public mailbox providers are refused (gmail.com, googlemail.com, outlook.com, hotmail.com, live.com, msn.com, yahoo.com, ymail.com, icloud.com, me.com, mac.com, aol.com, proton.me, protonmail.com, pm.me, gmx.com, gmx.net, mail.com, zoho.com, yandex.com, yandex.ru, fastmail.com, hey.com, tutanota.com, tuta.io).

Verification token: 16 random bytes as 32 lowercase hex chars, generated at claim time and stored. TXT record: the admin publishes a TXT record AT THE DOMAIN ITSELF (the apex `<domain>`, not a `_prefix` label) whose value is exactly `onecli-verification=<token>`. Verify performs a DNS TXT lookup on the domain; each record's chunks are joined before comparison; the match must be exact against the whole record; resolver errors (ENOTFOUND, ENODATA, SERVFAIL) are treated as "not there yet"; already-verified rows return immediately without a DNS call (idempotent). States: `pending` (verifiedAt null) → `verified` (verifiedAt set); there is no "failed" state and no expiry. `emailDomainOf(email)` applies the same normalization to the part after the last `@` (null when absent/invalid) and is the comparison key used by SSO trust and enforcement.

What a verified domain means downstream: it is the org's proof of ownership over every address on the domain — SSO home-realm discovery, JIT joins, identity relinking, and require-SSO enforcement all key on `verifiedAt != null`. Nothing in the free edition consumes it besides those SSO surfaces; a fork that ships domains without SSO must decide what verification unlocks.

### 8.2 SSO trust (`sso-trust.ts`)

- `findSsoOrgForIdentity(identityProviders[], email)`: unentitled → null with zero queries; candidates = provider names lowercased that start with `org-`; none → null; email domain invalid → null; a live (status ≠ disabled) SSO connection whose Cognito provider name is among the candidates AND a verified domain row for the email's domain in that SAME org → `{ organizationId, connectionId, cognitoProviderName }`; else null. Two-leg rule: org B's IdP cannot vouch for `a@orgA.com`.
- `lookupSsoForEmail(email)` (home-realm discovery): verified domain row → its org → a live connection → `{ provider, enforced: org.ssoRequired }` else null; never reveals whether a user exists.
- Consumers: the JIT service, SSO enforcement, the login lookup route, and the FREE `lib/identity-conflict.ts` (a session may re-point an existing user's auth id only if email is verified, or Google-federated, or an SSO session whose org verified the domain; both outcomes audited UPDATE/AUTH with success/failure).

### 8.3 SSO enforcement (`enforceSsoSession`, the `SessionEnforcer` slot; cloud only)

For every authenticated SESSION (never API keys): no usable email domain → allow; no verified domain with `ssoRequired` on its org → allow (one indexed query); the session arrived through that org's own SSO connection → allow; the member has `ssoExempt` → allow; otherwise deny with `{ error: "Your organization requires single sign-on. Sign in through your identity provider.", code: "sso_required" }` → the auth middleware answers 401 with that message/code. Domain-keyed: non-members with an enforced-domain email are also rejected. DB errors propagate (fail closed). The web mirrors it in `resolve-user.ts` and several server actions.

Enforcement route `/org/sso/enforcement` (gate `sso`, admin): GET → `{ ssoRequired, hasActiveConnection, hasVerifiedDomain, canRequire, exemptMemberCount }`; PATCH `{ ssoRequired: boolean }`: enabling is plan-gated and requires an ACTIVE connection and a verified domain (400 naming the missing leg: `Requiring SSO needs an active SSO connection. Complete a first sign-in through your IdP.` / `Requiring SSO needs a verified domain. Verify your company domain first.`); disabling is never gated; same-value → no write, no audit; otherwise audited UPDATE/ORGANIZATION `{ ssoRequired }`.

### 8.4 SSO connections (`/org/sso/connections`; Cognito-backed; cloud only)

One connection per org (CONFLICT `This organization already has an SSO connection.`). Types `saml` (exactly one of https `metadataUrl` or `metadataXml` 100..512000 chars) or `oidc` (https `issuer`, `clientId` ≤256, `clientSecret` ≤1024). Status lifecycle `pending` → `active` (flipped by the FIRST successful SSO login, audited UPDATE/SSO_CONNECTION source `sso-jit` `{ connectionId, status: "active", trigger: "first-sso-login" }`) → `disabled` (full Cognito teardown, prior status remembered and restored on enable; never re-minted as active). Every Cognito-touching operation runs under one global Redis lock (`api:lock:cognito-client`, TTL 60s, acquire timeout 10s → CONFLICT `Another SSO configuration change is in progress. Try again in a moment.`). Credentials are encrypted at rest with the crypto seam and never returned. Routes: GET (ungated list), POST (gated, 201, audited CREATE `{ connectionId, cognitoProviderName, type }`), PATCH (only `enabled:true` is gated; audited UPDATE with `enabled` when present), DELETE (never gated, audited DELETE `{ connectionId }`), POST `/:id/test` (gated, throttled 10/min per org, no audit; SAML: metadata reachable / is EntityDescriptor / cert validity; OIDC: discovery reachable / issuer matches). Disabling or deleting while `ssoRequired` is on → CONFLICT `This organization requires SSO. Turn off "Require single sign-on" before disabling|deleting the connection.` Cross-org → 404. Public login lookup: POST `/auth/sso/lookup` `{ email }` (gate `sso`, throttled 20/min per IP, no auth) → `{ sso: false }` or `{ sso: true, provider, enforced }`.

### 8.5 Member provisioning (claim links)

- POST `/team/provisions` (gate `provisioning`; admin; lenient body — `{}`, absent or malformed JSON all mint with defaults): `{ role: "admin"|"member" = member, skipOnboarding = true }`; unknown role → 400. Mints atomically: a placeholder user (`provision-<uuid>@onecli.internal`, auth id `provision-<uuid>`, onboarding completed when skipOnboarding), a membership with the requested role, a workspace named `Default` (slug `default-<userId8>`) with a pre-generated API key and an owner binding, and a `user_provisions` row (32-byte hex token, status `pending`, expires in 7 days). Before minting: `assertEntitled("provisioning")`, a non-fatal sweep of expired provisions, then the seat cap. Response 201 with the PUBLISHED wire shape and exactly these keys: `{ id, userId, projectId (= workspaceId, legacy name), apiKey, claimUrl: "<appUrl>/claim?token=<token>", expiresAt }`. Audited CREATE/PROVISION `{ provisionId, userId, workspaceId, role }` — never the token, claim URL or key.
- POST `/provisions/claim` (gate `provisioning`; session only, NOT the auth middleware — the claimer has no org yet): `{ token }` strict; 401 without a session or a user; 400 `A token is required`; service refusals → 400 `{ error: message }`; other faults 500 without internals; 200 `{ organizationId, organizationName }`; audited ACCEPT/PROVISION against the JOINED org `{ email }`.
- `claimProvision(token, realUserId, realEmail, realAuthId)`: entitlement first (links minted while licensed die unlicensed); unknown → NOT_FOUND `Invalid claim link`; not pending → CONFLICT `This provision has already been claimed or expired`; expired → flips status to `expired` and BAD_REQUEST `This provision link has expired`; pre-minted workspace gone → CONFLICT `This provision is no longer available`. Compare-and-set `pending → claiming` inside the transaction so concurrent claims yield exactly one winner (loser → CONFLICT `This provision has already been claimed`). Branch A (claimer already exists as a user): if they already hold a membership in the org (suspended counts as existing) the placeholder membership is deleted, else it is re-pointed to the real user; workspace creator, name (`workspaceNameForOwner`), owner binding (upsert), API keys are transferred; onboarding marked when requested; provision row and placeholder user deleted. Branch B (first-time user): the placeholder user row is rebound in place (email + auth id), membership email updated, workspace renamed, owner binding upserted, keys' email updated, provision marked `claimed`; refuses with CONFLICT `This account is already registered with another user` if the auth id already belongs to someone.
- `findPendingProvisionByToken` (claim page): unentitled → null; returns `{ organizationName }` only for pending rows (a time-expired pending link still renders; the claim marks it expired with a readable error).
- `listProvisions` (sweeps first; pending only, newest first: `{ id, role, provisionedByEmail, expiresAt, createdAt }`), `cancelProvision` (NOT_FOUND `Provision not found` unless pending in org; unwinds workspace content, memberships, provision row, placeholder user, flushes keys), `cleanupExpiredProvisions` (reaps `pending` and `expired` rows past `expiresAt`, one poison row never aborts the sweep).
- Session hook: a claimer's first session carries `?fromClaim` so the cloud signup ping/welcome email fire with source "provision claim".

### 8.6 SCIM 2.0 (`/scim/v2`, own Hono app, cloud/licensed)

- Auth: `Authorization: Bearer oc_scim_<48 hex>`; the DB stores sha-256 only; every request re-checks entitlement; missing/unknown/revoked token → identical hint-free 401 `{ schemas:[Error], status:"401", detail:"Authentication failed." }` with `WWW-Authenticate: Bearer realm="scim"`; `lastUsedAt` touched fire-and-forget; rate limit 600/min per token (429 generic envelope). Discovery endpoints sit behind the token; `/Me` → 501; unknown routes → SCIM-shaped 404; a `filter` on configuration endpoints → 403.
- Tokens: `/org/scim/tokens` (gate `sso`, admin): GET non-revoked `{ id, label, lastUsedAt, createdAt }`; POST `{ label }` (strict, 1..64) gated → 201 row + `token` (shown once), audited CREATE/SCIM_TOKEN `{ tokenId, label }`; DELETE soft-revokes (idempotent; never plan-gated), audited DELETE/SCIM_TOKEN `{ tokenId }`; cross-org/unknown → 404.
- Users: identity key is `userName` (email); `externalId` is NOT stored for users (an `externalId eq` filter → 400 invalidFilter with guidance). GET list with 1-based `startIndex`/`count` (default 100, max 500, negative → 0) or a single `userName eq` filter (unmatched → 200 with `totalResults: 0`, never 404 — Entra's Test Connection). POST provisions (existing member → 409 `uniqueness`; `active:false` provisions suspended). PUT/PATCH map `userName` (rename, guarded: sole-org members only, otherwise 400 `mutability`; collision 409 `uniqueness`), `displayName`, `name` (components stored verbatim, dotted no-path keys supported), `active` (Entra "True"/"False" strings coerced; same-state flip is a no-op with no audit; owner deactivation → 400 detail). Unmapped attributes are accepted and ignored. DELETE = the same reversible suspension (never destructive); a repeat DELETE → 404. Deactivation/reactivation through the directory core are idempotent; the owner guard fires before the self-guard so the SCIM actor (the owner) gets a clear message.
- Groups: `source: "scim"` rows; SCIM owns displayName, members and externalId (unique per org+source; collision 409), never the role mapping; nested groups rejected (member entries must be `{ value: <user id> }`); filters `displayName eq` (case-insensitive) / `externalId eq`; `excludedAttributes=members` omits the members array; PATCH supports path and no-path forms, both Okta member-remove syntaxes, replace/clear; cross-org → 404.
- Audit: every SCIM write is attributed to the org OWNER (`resolveScimActor`; no owner = NOT_FOUND `Organization owner not found`), source `scim`, with `scimTokenId`/`scimTokenLabel` in metadata, and flushes the org gateway cache.
- ServiceError → SCIM mapping: CONFLICT→409 uniqueness; NOT_FOUND→404; BAD_REQUEST/UNPROCESSABLE/GONE/RATE_LIMITED→400 invalidValue; FORBIDDEN→403.

### 8.7 JIT membership (`ensureSsoJitMembership`, the `ensureSessionMembership` session hook)

On every session: resolve the SSO org via trust; none → return. Flip the connection pending→active (audited once). If the user already has ANY membership (suspended included) → reconcile mappings (source `sso-login`) and stop (never re-mint a suspended user). If the org's `jitEnabled` → in one transaction create the `member` membership + personal workspace (`memberProvisionOps`), audited CREATE/MEMBER source `sso-jit` `{ organizationId, role: "member", connectionId }`, then reconcile. A concurrent unique violation is success; any other error is logged and swallowed — session resolution never fails because of JIT.

Domains: **KEEP** the contract above verbatim (the fork ships domains). SSO connections/enforcement/lookup, SCIM, JIT, the `ssoExempt` flag: **DROP** unless the fork brings its own IdP integration (all of it is Cognito-shaped). Provisioning (claim links): **TRIM** — self-host-neutral and useful for scripted onboarding, but it depends on the seat cap (no-op) and placeholder cleanup; keep only if the `projectId` wire contract matters to you.
